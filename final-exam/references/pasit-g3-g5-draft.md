### ปรับอ้างอิงจาก G1/G2 ที่ได้รับ

ตรวจร่วมกับไฟล์ `g1-g2-wijitsilp.md` ที่ผู้ใช้ส่งมาเมื่อ 23 ตุลาคม 2026 แล้วในระดับร่าง ไม่ถือเป็นการรับรองว่ามนุษย์ตรวจหรืออนุมัติแล้ว รหัส FX ด้านล่างเป็นข้อเสนอใหม่ของ G2 ไม่ใช่ baseline ที่อนุมัติ

| CAP-FX-02 เตือนก่อนซักเสร็จ 5 นาที | FR-04 ส่วนเดิม; FR-FX-01 สำหรับนโยบายใหม่ที่ยัง TBD | US-05, UC-02, AC-05/AC-FX-02 | SP-FX-04 |

**ขอบเขตที่ยังต้องตกลง:** G2 เปิด OI-FX-01 ครอบคลุมช่องทางในระบบด้วย ดังนั้นการแจ้งในเว็บและรายการแจ้งส่วนตัวของ CAP-FX-01/SP-FX-06 เป็นข้อเสนอของ G3 สำหรับรุ่นแรก ยังไม่ใช่ช่องทางที่ทีม/เจ้าของระบบยืนยัน ต้องให้ G2 ระบุพฤติกรรมและข้อมูลจัดเก็บเพิ่มเติมหากเลือกแนวทางนี้ ส่วน audit ขั้นต่ำของ G5 ยังไม่มี requirement ID ใน G2 ที่ได้รับ

**เกณฑ์ข้อความภายนอกตาม G2:** NFR-FX-01/AC-FX-04 เสนอให้เนื้อหามีเพียงประเภทเหตุการณ์และรหัสคิวที่จำเป็น ไม่มีชื่อจริง เลขห้อง เบอร์โทร หรือข้อมูลผู้ใช้อื่น ข้อมูลปลายทางที่ใช้ส่งต้องแยกจากเนื้อหาและยัง TBD ตามวิธีเชื่อมต่อ ไม่ใช้ข้อเสนอ privacy นี้เป็นเหตุผลเปิดเผยข้อมูลบนหน้าสาธารณะ

## G3 — Design Strategy หลัง CR-FX-01

### G3.1 ขอบเขตความสามารถใหม่

Build now หมายถึงทำเส้นทางที่ทดสอบได้ในรุ่นแรก; Overview หมายถึงคงในภาพรวม ข้อมูล และกติกา แต่ยังไม่ลงรายละเอียดครบ; Later หมายถึงเลื่อนการพัฒนา ไม่ลบ requirement ออกจาก SRS

| รหัสทำงาน / ความสามารถ | ที่มา | ระดับที่เสนอ | เหตุผลและขอบเขต |
|---|---|---|---|
| CAP-FX-01 แจ้งผู้ใช้ที่เกี่ยวข้องเมื่อสถานะคิวหรืองานหลักเปลี่ยน | CR-FX-01(1), FR-04, FR-05 และ SRS §7 | Build now | ใช้การแจ้งในเว็บเป็นเส้นทางรุ่นแรกที่เสนอ ต้องให้ G2 ระบุรายการเหตุการณ์และผู้รับที่แน่นอน ห้ามส่งให้ผู้ใช้ทุกคนโดยไม่จำเป็น |
| CAP-FX-02 เตือนก่อนซักเสร็จโดยไม่มีผู้ใช้กด | CR-FX-01(2), FR-04, CT-01 | Build now | ใช้เวลาจำลองการซักเป็นฐาน SRS เดิมระบุ 5 นาที ไม่ใช่ตัวเลขที่ตั้งใหม่ แต่การยืนยันว่าจะคงค่านี้ภายใต้ CR อยู่ใน DD-FX-02 |
| CAP-FX-03 ผู้ใช้เลือก opt-in/ถอนการเลือกรับผ่านช่องทางภายนอก | CR-FX-01(3), FR-FX-02, BR-FX-01, DR-FX-01 | Build now | เก็บและตรวจ preference ฝั่ง server ตาม G2; AC-FX-03/05 ตรวจการถอน opt-in และสิทธิ์เจ้าของบัญชี แต่ไม่แสดงว่าการส่งภายนอกพร้อมใช้ก่อนตัดสินช่องทาง |
| CAP-FX-04 จำกัดข้อมูลในข้อความและส่งเฉพาะผู้เกี่ยวข้อง | CR-FX-01(3), NFR-01, BR-04 | Build now | ตรวจผู้รับและข้อมูลขั้นต่ำที่ server หน้าจอสาธารณะยังแสดงเฉพาะรหัสคิว เกณฑ์ข้อมูลข้อความภายนอกต้องให้ผู้ดูแลยืนยันเพิ่มเติม |
| CAP-FX-05 เชื่อมต่อช่องทางแจ้งเตือนภายนอก | CR-FX-01(3), OI-01 | Overview | แสดงระบบภายนอกเป็น Extension / TBD และจุดเชื่อมต่อไว้ก่อน ผู้ให้บริการ วิธีเชื่อมต่อ และ protocol ยังไม่ตกลง ไม่อ้างว่าส่งจริงได้แล้ว |
| CAP-FX-06 ระบุเวลาเตือนสำหรับกำหนดสำคัญอื่นที่ไม่มีใน SRS | CR-FX-01(2) | Overview | เก็บคำถามและตำแหน่งกติกาไว้ แต่ยังไม่เปิดใช้กฎที่ไม่มีเหตุการณ์/เวลาที่ตกลง ห้ามนำค่า 5 นาทีของการซักไปใช้กับทุกเหตุการณ์ |
| CAP-FX-07 เปิดใช้งานการส่งจริงผ่านช่องทางภายนอก | CR-FX-01(3), OI-01 | Later | รอคำตอบ DD-FX-01 และการทดสอบกับช่องทางที่เลือก จึงเสนอเป็นรุ่นถัดไปโดยต้องให้ผู้มีอำนาจตัดสินยอมรับขอบเขต |
| เชื่อม IoT จริงและรับชำระเงินออนไลน์ | SRS §1.3, CT-01, CASE_CARD.md | ไม่ทำในวิชานี้ | อยู่นอกขอบเขตเดิม และ CR-FX-01 ไม่ได้ขอให้เพิ่ม |

ไม่จัดทุกข้อเป็น Build now แม้ผู้เสนอร้องขอ เพราะการเชื่อมต่อภายนอกและค่าที่ยังไม่ตกลงทำให้กำหนดงานและทดสอบการส่งจริงไม่ได้ ข้อเสนอนี้ส่งมอบการแจ้งในเว็บและการเตือนตามเวลาที่ตรวจสอบได้ก่อน พร้อมรักษา opt-in และความเป็นส่วนตัว การเลื่อนการส่งภายนอกเป็นข้อเสนอให้เจ้าของระบบตัดสิน ไม่ใช่การอนุมัติ CR โดยกลุ่ม

### G3.2 Driver check

ไม่พบ driver เดิมที่กรอกเสร็จใน W10 จึงสังเคราะห์ driver ต่อไปนี้จาก SRS และ CR โดยยังเป็น Proposed

| Driver | แหล่งอ้างอิง | ผลจาก CR และผลต่อการออกแบบ |
|---|---|---|
| D-FX-01 คิวต้องเป็นธรรมและสถานะเชื่อถือได้ | FR-02, FR-03, BR-01, BR-02 | การแจ้งเตือนใช้สถานะที่บันทึกสำเร็จแล้ว ไม่ให้ข้อความแจ้งเตือนเปลี่ยนสิทธิ์คิวเอง API ตรวจหนึ่งคิวต่อบัญชีและเงื่อนไข no-show; Scheduled Job ทำงานตามเวลาจากฐานข้อมูล |
| D-FX-02 ปกป้องข้อมูลและควบคุมสิทธิ์ | NFR-01, BR-03, BR-04 และ CR-FX-01(3) | เพิ่มการตรวจ opt-in และข้อมูลข้อความขั้นต่ำที่ server; การปิดปรับปรุงยังเป็นสิทธิ์ผู้ดูแลหอพัก ไม่ย้ายการตรวจไปพึ่งหน้าจอ |
| D-FX-03 แจ้งเตือนตามเวลาโดยไม่ต้องมีใครเปิดหน้าเว็บ | FR-04, CR-FX-01(2) | ต้องมีงานตามเวลาฝั่ง server เสนอ Scheduled Job โดยใช้ Node.js ไม่ใช้ timer ใน browser เป็นกลไกหลัก |
| D-FX-04 มือถือและความทันเวลาของสถานะ | NFR-02, NFR-03, NFR-04 | Web App เป็น React และ API เป็น Node.js + Express; ค่า 3 วินาทีของ NFR-03 ใช้กับการอัปเดตสถานะ ไม่ถือเป็น SLA ของการส่งภายนอก; วิธีอัปเดตและหลักฐาน load test ยังต้องตัดสิน/ตรวจใน G4 |
| D-FX-05 แยกงานหลักจากบริการภายนอกที่ยังไม่ตกลง | OI-01 และ CR-FX-01 | เสนอให้การบันทึกคิวสำเร็จไม่ผูกกับผลส่งภายนอก รายละเอียด failure/retry และข้อมูลสถานะการส่งเป็น open decision ไม่กำหนดจำนวนครั้งเอง |

### G3.3 Design Spine ที่เพิ่มหรือเปลี่ยน

เนื่องจากไม่มี Spine เดิมที่เสร็จ ตารางนี้เป็น proposed Spine เพื่อส่งต่อ G4 ส่วน UC/AC ของความสามารถใหม่รอ G2 กำหนด ID จริง

ชื่อ container ที่เสนอให้ใช้ตรงกัน: **Web App**, **API Application**, **Database**, **Scheduled Job** ส่วน **External Notification Channel** เป็นระบบภายนอก Extension / TBD ไม่ใช่ container ที่ทีมควบคุม

| ขั้น | การกระทำ / ผลลัพธ์ | ที่มา | ระดับ W10 | เส้นทาง W11 และตำแหน่งตรวจ rule |
|---|---|---|---|---|
| SP-FX-01 | นักศึกษาหอพักดูสถานะและจองคิว | FR-01, FR-02, BR-01 | Build now | Web App → API Application → Database; API ตรวจบัญชีและหนึ่งคิวต่อคน |
| SP-FX-02 | ผู้มีสิทธิ์เปลี่ยนสถานะงาน เช่น ถึงคิว เริ่มซัก หรือปิดปรับปรุง | FR-03, FR-05, BR-02, BR-03, SRS §7 | Build now | Web App หรือ Scheduled Job → API Application → Database; API ตรวจสิทธิ์และเงื่อนไขสถานะก่อนบันทึก โดยชุด transition ต้องตรง G2 |
| SP-FX-03 | ระบบระบุผู้เกี่ยวข้องและสร้างรายการแจ้งหลังบันทึกสถานะสำเร็จ | CR-FX-01(1), FR-04 | Build now | API Application → Database; API ตรวจความสัมพันธ์ผู้รับกับงานและข้อมูลที่เปิดเผย เสนอเพิ่มข้อมูลรายการแจ้งใน G2 |
| SP-FX-04 | เตือนก่อนซักเสร็จอัตโนมัติตามเวลาจำลอง | CR-FX-01(2), FR-04, CT-01 | Build now | Scheduled Job → API Application → Database; Job ตรวจเวลาถึงกำหนด API ตรวจสถานะล่าสุดและผู้รับอีกครั้ง ไม่พึ่ง browser เปิดอยู่ |
| SP-FX-05 | นักศึกษาหอพักเลือก/ถอน opt-in ภายนอก | FR-FX-02, BR-FX-01, DR-FX-01; UC-FX-01; AC-FX-03/05 | Build now | Web App → API Application → Database; API ตรวจว่าแก้ preference ของบัญชีตนเองและตรวจค่าปัจจุบันก่อนส่ง; รูปแบบปลายทาง/ระยะเก็บยังรอ OI-FX-01/05 |
| SP-FX-06 | ผู้ใช้เปิดดูรายการแจ้งในเว็บของตน | CAP-FX-01, CAP-FX-04 | Build now | Web App → API Application → Database; API กรองเจ้าของรายการและข้อมูลขั้นต่ำ เป็นช่องทางรุ่นแรกที่เสนอให้ G2 ตรวจรับ |
| SP-FX-07 | ส่งผ่านภายนอกเมื่อเปิดใช้และผู้ใช้ opt-in | CR-FX-01(3), OI-01 | Overview; การส่งจริง Later | API Application → External Notification Channel; วิธีเชื่อมต่อ/protocol TBD ตรวจ preference ปัจจุบันก่อนส่ง ไม่ใส่ชื่อผู้ให้บริการในภาพ |

ข้อเสนอ container: เพิ่ม Scheduled Job เพราะมี requirement ให้เกิดตามเวลาโดยไม่มีคนกด ใช้ Node.js รันฝั่ง server ที่ทีมควบคุม ส่วนจะรันร่วมเครื่องหรือแยก process และวิธีเรียก API ให้ G4 ระบุเป็น Proposed/TBD ไม่เพิ่ม broker หรือ notification microservice หากยังไม่มี FR/NFR บังคับ

### G5.2 Decision card — DEC-FX-02B-01

**สถานะ: Proposed**

**ตัดสินใจที่เสนอ:** รักษาวงจรคิวหลัก การตรวจสิทธิ์ฝั่ง API และความเป็นส่วนตัวไว้ใน Build now พร้อมเสนอให้มี audit ขั้นต่ำสำหรับการเปลี่ยนสถานะสำคัญ ไม่ทำหน้ารายงาน audit แบบละเอียดในรุ่นแรก เลื่อน FR-07 และการส่งภายนอกจริงออกไป

**เพราะ:** BR-01/BR-02 ป้องกันการกั๊กคิวและ no-show, BR-03 จำกัดการปิดปรับปรุงให้ผู้ดูแล และ BR-04/NFR-01 ปกป้องหน้าสาธารณะ การตัดสิทธิ์ทำให้ระบบผิดข้อกำหนดเดิม ส่วนประวัติการเปลี่ยนสถานะช่วยตรวจสอบข้อโต้แย้ง แต่เป็น proposed requirement ที่ต้องตรวจขอบเขตข้อมูลก่อน

**ทางเลือกที่ไม่เลือก:** (1) ตัดการตรวจสิทธิ์และไม่เก็บประวัติใดเลย เสี่ยงแก้สถานะโดยไม่มีสิทธิ์และตรวจสอบเหตุการณ์ไม่ได้ (2) ทำทุกฟังก์ชันเท่าเดิม ยังไม่มี effort สนับสนุนว่าจะเสร็จในเวลาที่ลดลง

**ผลที่ตามมา:** รุ่นแรกมีฟังก์ชันรองน้อยลง และภายนอกยังไม่พร้อมส่งจริง ต้องแจ้งข้อจำกัดนี้ให้เจ้าของระบบยอมรับ; API/Database รับผิดชอบสิทธิ์และบันทึก audit ไม่จำเป็นต้องเพิ่ม audit container แยกเพียงเพื่อเก็บประวัติ

**ขอบเขต audit ที่เสนอ:** ผู้กระทำหรือเหตุการณ์ระบบ, รายการที่ถูกเปลี่ยน, สถานะก่อน/หลัง, เวลา สำหรับเหตุการณ์สำคัญ เช่น ปิดปรับปรุงและข้ามคิว; ไม่บันทึกเนื้อหาส่วนบุคคลเกินจำเป็น สิทธิ์อ่าน ระยะเวลาเก็บ และรายการเหตุการณ์สุดท้ายเป็น TBD ใน DD-FX-05

**อ้างอิง:** FR-01–FR-05, BR-01–BR-04, NFR-01, CR-FX-01 และ CR-FX-02B; audit ยังไม่มี ID ใน SRS เดิม ให้ G2 กำหนด ID ใหม่ก่อนส่ง
