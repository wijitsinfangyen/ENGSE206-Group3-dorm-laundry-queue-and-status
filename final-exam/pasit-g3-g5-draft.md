## G3 — Design Strategy หลัง CR-FX-01

### G3.1 ขอบเขตความสามารถใหม่

Build now หมายถึงทำเส้นทางที่ทดสอบได้ในรุ่นแรก; Overview หมายถึงคงในภาพรวม ข้อมูล และกติกา แต่ยังไม่ลงรายละเอียดครบ; Later หมายถึงเลื่อนการพัฒนา ไม่ลบ requirement ออกจาก SRS

### G3.2 Driver check

### G3.3 Design Spine ที่เพิ่มหรือเปลี่ยน

เนื่องจากไม่มี Spine เดิมที่เสร็จ ตารางนี้เป็น proposed Spine ที่ผูกกับ requirement/model/AC จาก G2 ฉบับแก้ไขตามตารางอ้างอิงด้านบน และตรวจเทียบเส้นทางกับ G4 รอบล่าสุดแล้วในระดับเอกสาร

ชื่อ container ที่เสนอให้ใช้ตรงกัน: **Web App**, **API Application**, **Database**, **Scheduled Job** ส่วน **External Notification Channel** เป็นระบบภายนอก Extension / TBD ไม่ใช่ container ที่ทีมควบคุม

| ขั้น | การกระทำ / ผลลัพธ์ | ที่มา | ระดับ W10 | เส้นทาง W11 และตำแหน่งตรวจ rule |
|---|---|---|---|---|
| SP-FX-01 | นักศึกษาหอพักดูสถานะและจองคิว | FR-01, FR-02, BR-01 | Build now | Web App → API Application → Database; API ตรวจบัญชีและหนึ่งคิวต่อคน |
| SP-FX-02 | ผู้มีสิทธิ์เปลี่ยนสถานะงาน เช่น ถึงคิว เริ่มซัก หรือปิดปรับปรุง | FR-03, FR-05, BR-02, BR-03, SRS §7; G5 เพิ่ม FR-FX-04/DR-FX-02 | Build now | Web App หรือ Scheduled Job → API Application → Database; API ตรวจสิทธิ์และเงื่อนไขสถานะ ส่วน G5 ให้บันทึกสถานะพร้อม audit ใน transaction เดียวกัน หาก audit ล้มเหลว rollback ไม่ยืนยันสถานะใหม่และไม่แจ้งว่าสำเร็จ ตาม AC-FX-08 |
| SP-FX-03 | ระบบระบุผู้เกี่ยวข้องและสร้างรายการแจ้งหลังบันทึกสถานะสำเร็จ | CR-FX-01(1), FR-04, FR-FX-03 | Build now | API Application → Database; API ตรวจเจ้าของคิว/ข้อมูลที่เปิดเผย เก็บรายการสำหรับอ่านย้อนหลัง; ภายใต้ G5 ต้องรอทั้งสถานะและ audit commit สำเร็จก่อนสร้างผลแจ้งสถานะใหม่ |

### G5.2 Decision card — DEC-FX-02B-01

**สถานะ: Proposed**

**ตัดสินใจที่เสนอ:** รักษาวงจรคิวหลัก การตรวจสิทธิ์ฝั่ง API ความเป็นส่วนตัว และรายการแจ้งในเว็บตาม FR-FX-03 ไว้ใน Build now พร้อม audit ทุกการเปลี่ยนสถานะคิวหรือเครื่องที่สำเร็จตาม FR-FX-04 และให้ผู้ดูแลที่มีสิทธิ์อ่านผ่านหน้าหรือมุมมองแบบง่ายได้ตาม BR-FX-02/UC-FX-03 การค้นหาและรายงาน audit ขั้นสูงเป็น Later เลื่อน FR-07 และการส่งภายนอกจริงออกไป

**เพราะ:** BR-01/BR-02 ป้องกันการกั๊กคิวและ no-show, BR-03 จำกัดการปิดปรับปรุงให้ผู้ดูแล และ BR-04/NFR-01 ปกป้องหน้าสาธารณะ การตัดสิทธิ์ทำให้ระบบผิดข้อกำหนดเดิม ส่วนประวัติการเปลี่ยนสถานะช่วยตรวจสอบข้อโต้แย้ง แต่เป็น proposed requirement ที่ต้องตรวจขอบเขตข้อมูลก่อน

**ทางเลือกที่ไม่เลือก:** (1) ตัดการตรวจสิทธิ์และไม่เก็บประวัติใดเลย เสี่ยงแก้สถานะโดยไม่มีสิทธิ์และตรวจสอบเหตุการณ์ไม่ได้ (2) ทำทุกฟังก์ชันเท่าเดิม ยังไม่มี effort สนับสนุนว่าจะเสร็จในเวลาที่ลดลง

**ผลที่ตามมา:** รุ่นแรกมีฟังก์ชันรองน้อยลง และภายนอกยังไม่พร้อมส่งจริง ต้องแจ้งข้อจำกัดนี้ให้เจ้าของระบบยอมรับ; API/Database รับผิดชอบสิทธิ์และบันทึก audit ไม่จำเป็นต้องเพิ่ม audit container แยกเพียงเพื่อเก็บประวัติ

**ขอบเขต audit ที่เสนอ:** ทุกการเปลี่ยนสถานะคิวหรือเครื่องที่สำเร็จ เก็บรหัสเหตุการณ์ ประเภทรายการ/รหัสคิวหรือเครื่อง สถานะก่อน/หลัง เวลาระบบ ผู้ดำเนินการอ้างอิงบัญชีหรือระบุว่าเป็นระบบ และเหตุผลเมื่อมี ตาม DR-FX-02 หลีกเลี่ยงชื่อจริง เลขห้อง และเนื้อหาข้อความส่วนบุคคล ไม่อ้างรวม access log หรือประวัติส่งข้อความทั้งหมด

**ความสอดคล้องและสิทธิ์:** API ตรวจ rule แล้วบันทึกสถานะพร้อมประวัติใน transaction เดียวที่ Database; ถ้า audit ล้มเหลวต้อง rollback และไม่แจ้งว่าสถานะใหม่สำเร็จตาม AC-FX-08 ผู้ดูแลหอพักที่มีสิทธิ์อ่านประวัติได้ นักศึกษาอ่านไม่ได้ และห้ามแก้/ลบผ่านงานทั่วไปของผู้ใช้หรือผู้ดูแลตาม BR-FX-02/AC-FX-09 ส่วนระยะเก็บรักษา ผู้ดูแลข้อมูล และข้อยกเว้นการลบยัง TBD ใน DD-FX-05/OI-FX-05 วิธี transaction นี้เป็นข้อเสนอออกแบบให้ G4 ตรวจ ไม่ใช่หลักฐานการทดสอบจริง

**อ้างอิง:** FR-01–FR-05, BR-01–BR-04, NFR-01, CR-FX-01 และ CR-FX-02B; G2 ฉบับแก้ไขเพิ่ม FR-FX-03/04, DR-FX-02, BR-FX-02, US-FX-02/03, UC-FX-02/03 และ AC-FX-06–09 แบบ Proposed ไม่ใช่ audit ใน baseline เดิม

หลังได้รับ G1/G2 ฉบับแก้ไข: มี requirement/model/AC สำหรับรายการแจ้งในเว็บและ audit แล้ว ไม่ต้องขอเพิ่ม ID สองเรื่องนี้ซ้ำ ประเด็นที่เหลือคือให้ปฐมพรตรวจชื่อ/เส้นทาง container, transaction สถานะพร้อม audit, สิทธิ์อ่านประวัติ และมุมมองอ่านแบบง่ายใน G4 รวมทั้งให้ทีมตรวจความครบของรหัสในบทสรุป/trace ของ G1/G2 โดยไม่ถือว่า CR ได้รับอนุมัติ
