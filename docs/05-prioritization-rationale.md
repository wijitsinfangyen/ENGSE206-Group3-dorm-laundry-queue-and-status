> ไฟล์นี้อธิบายเหตุผลว่าทำไม Requirement แต่ละข้อของระบบจองคิวและติดตามสถานะเครื่องซักผ้าหอพักจึงได้รับ Priority ตามที่กำหนด

## 1. หลักคิด

ทีมใช้ 4 คำถามในการพิจารณา Priority ของแต่ละ Requirement:

1. **Value:** Requirement นี้ช่วยแก้ปัญหาหลักให้ใคร และสร้างประโยชน์อย่างไร (เช่น ลดการเดินฟรี, ลดปัญหาการกั๊กคิว, ป้องกันการกินเหรียญ)?
2. **Risk:** หากไม่มี Requirement นี้ จะเกิดความล่าช้า ข้อมูลไม่ตรงจริง ผู้ใช้โต้แย้งกัน หรือเกิดการละเมิดความเป็นส่วนตัว (PDPA) หรือไม่?
3. **Urgency:** Requirement นี้จำเป็นต่อ Core Workflow หลักของระบบในรุ่นแรก (Release 1) หรือสามารถทำภายหลังได้?
4. **Dependency:** Requirement นี้ต้องรอข้อมูลหรือนโยบายจาก Stakeholder (ผู้ดูแลหอพัก/แม่บ้าน/ช่าง IT) ก่อนหรือไม่?

## 2. เหตุผลราย Requirement

| Req ID | Priority | เหตุผลหลัก | Trade-off / Dependency |
|---|---|---|---|
| **FR-01** | Must | การแสดงสถานะเครื่องซักผ้าเป็น Core Capability หลัก หากไม่มีความสามารถนี้ จะไม่สามารถแก้ปัญหาการเดินลงมาดูเครื่องฟรีของผู้พักอาศัยได้ | ต้องยืนยันรูปแบบการอัปเดตสถานะ (Simulation vs Sensor) |
| **FR-02** | Must | การกดเข้าคิวล่วงหน้าผ่านสมาร์ตโฟนช่วยแก้ปัญหาการนั่งคอยและการวางตะกร้ากั๊กคิวหน้าเครื่อง | ต้องมีกฎจำกัดจำนวนคิวต่อคนเพื่อป้องกันการกั๊กคิว (BR-01) |
| **BR-01** | Must | การจำกัดสิทธิ์จองได้ครั้งละ 1 คิว ช่วยกระจายสิทธิ์อย่างเป็นธรรมและป้องกันผู้ใช้คนเดียวจองหลายเครื่องพร้อมกัน | ต้องเชื่อมโยงกับการยืนยันตัวตนผู้ใช้งาน (User Auth) |
| **FR-03** | Must | ระบบ No-show Timeout ป้องกันการกั๊กคิวจากระยะไกล หากไม่มีระบบนี้ คิวจะสะสมและคนอื่นเสียโอกาส | ต้องยืนยันตัวเลขเวลาผ่อนผันที่แน่นอน (BR-02: 10 นาที) |
| **FR-04** | Must | การแจ้งเตือนก่อนเครื่องเสร็จและเมื่อถึงคิวช่วยให้ผู้ใช้มารับผ้าทันเวลา ลดปัญหาผ้าค้างเครื่อง | ต้องเลือก API ส่งข้อความที่เสถียรและไม่มีค่าใช้จ่ายส่วนเกิน |
| **FR-05** | Must | การรายงานเครื่องเสียและปิดรับคิวช่วยป้องกันไม่ให้นักศึกษาคนอื่นมาหยอดเหรียญซ้ำจนเงินกินเหรียญ | ต้องระบุ Authority ว่าผู้ดูแลหอพักเป็นผู้ปิดสถานะ (BR-03) |
| **NFR-01** | Must | การปกปิดข้อมูลส่วนบุคคล (PII) บน UI สาธารณะเป็นข้อบังคับด้านกฎหมาย (PDPA) และลดความกังวลเรื่องความปลอดภัย | ต้องออกแบบรหัสคิวสุ่มหรือชื่อย่อที่อ่านง่ายแต่ระบุตัวไม่ได้ |
| **NFR-02** | Must | หน้าจอต้องเป็น Mobile-first เพื่อให้นักศึกษาเช็กสถานะได้สะดวกรวดเร็วขณะอยู่ในห้องพัก | ต้องทดสอบ UI/UX บนหน้าจอมือถือหลายขนาด |
| **NFR-03** | Must | ข้อมูลสถานะและคิวต้องอัปเดตแบบ Real-time Latency ไม่เกิน 3 วินาที เพื่อป้องกันข้อมูลขัดแย้ง | พึ่งพาเสถียรภาพของระบบ Cloud Server และสัญญาณเน็ต |
| **FR-06** | Should | ระบบบันทึกจุดวางผ้าค้างเครื่องช่วยให้แม่บ้านทำงานง่ายขึ้น และช่วยให้นักศึกษาตามหาผ้าเจอ | ต้องยืนยันนโยบายหอพักและจุดจัดวางผ้าค้างเครื่องส่วนกลาง |
| **NFR-04** | Should | การรองรับ Concurrent Users ช่วง Peak Hours (18:00 - 22:00 น.) ช่วยให้ระบบไม่ล่มเมื่อคนใช้พร้อมกัน | ต้องทำ Performance Testing จำลองโหลดผู้ใช้งาน |
| **FR-07** | Could | รายงานสถิติเครื่องเสียย้อนหลังช่วยให้ผู้ดูแลหอพักนำไปแจ้งเจ้าของสัมปทานเพื่อปรับปรุงอุปกรณ์ | ต้องถามตัวชี้วัด (KPI) ที่ผู้ดูแลหอพักต้องการใช้จริง |
| **NFR-05** | Could | มาตรฐาน WCAG Accessibility ช่วยให้ผู้ใช้ที่มีข้อจำกัดอ่านหน้าจอใต้หอพักได้ง่ายขึ้น | สามารถปรับแต่งโทนสีและขนาดฟอนต์เพิ่มเติมในภายหลังได้ |
| **FR-08** | Won't | ระบบควบคุมวงจรเครื่องจริงและการชำระเงินออนไลน์ อยู่นอกขอบเขตของโครงงานรายวิชานี้ | ตัดออกในเฟสแรกเนื่องจากข้อจำกัดงบประมาณและ Hardware |

## 3. สิ่งที่ไม่ได้เลือกเป็น requirement ทันที

| สิ่งที่พบใน Week04 | เหตุผลที่ยังไม่กำหนดเป็น Requirement |
|---|---|
| บังคับเชื่อมต่อวงจร IoT กับเครื่องซักผ้าดั้งเดิมทุกเครื่อง | เป็น Hardware Constraint มีค่าใช้จ่ายสูง จึงเปลี่ยนเป็นระบบ Timer Simulation ในเฟสแรก |
| กำหนดให้ใช้ LINE Notify เป็นช่องทางแจ้งเตือนหลักเพียงช่องทางเดียว | ยังเป็น Channel Preference ต้องสอบถามความสะดวกของนักศึกษาส่วนใหญ่ก่อน |
| ตัดสิทธิ์หรือแบนผู้ใช้ที่ No-show ทันทีโดยไม่แจ้งเตือน | มาตรการรุนแรงเกินไป อาจเกิดข้อโต้แย้งหากระบบเน็ตของผู้ใช้หลุด ต้องมี Grace Period ก่อน |
| อนุญาตให้นักศึกษาเปิด-ปิดสถานะเครื่องซักผ้าได้เองเมื่อพบเครื่องเสีย | มีความเสี่ยงในการกลั่นแกล้งกัน จึงต้องให้ผู้ดูแลหอพัก (Dorm Admin) เป็นผู้อนุมัติเท่านั้น |
| กำหนดให้แม่บ้านต้องไปยกผ้าค้างเครื่องออกทันทีที่ซักเสร็จเกิน 15 นาที | เป็นภาระงานที่เกินขอบเขตของแม่บ้าน และยังไม่มีนโยบายหอพักรองรับการย้ายทรัพย์สินผู้พัก |
| ระบบคืนเงินอัตโนมัติเมื่อเครื่องกินเหรียญ | อยู่นอกขอบเขต (Out of Scope) และไม่มีช่องทางเชื่อมต่อระบบการเงินในโครงงานวิชานี้ |

## 4. บทเรียนสำหรับนักศึกษา

- **Priority สูงไม่ได้หมายความว่า Requirement สมบูรณ์แล้ว:** เช่น FR-03 (No-show Timeout) เป็น Must Have แต่ยังต้องรอสรุปตัวเลขนาทีที่แน่นอนจาก Stakeholder
- **Requirement อาจมีความสำคัญต่อระบบ แต่ยังต้องตรวจสอบรายละเอียดเพิ่มเติมก่อนนำไปพัฒนาจริง:** เช่น การแจ้งเตือน (FR-04) สำคัญมาก แต่ต้องเลือกเทคโนโลยี API ให้เหมาะกับงบประมาณ
- **อย่าเปลี่ยนข้อเสนอของ Stakeholder ให้เป็น Requirement ทันที:** เช่น การเสนอให้ย้ายผ้าค้างเครื่องทันที เป็นเพียงแนวคิดแก้ปัญหา ต้องตรวจสอบระเบียบหอพักเรื่องสิทธิ์ในทรัพย์สินก่อน
- **ถ้ายังไม่มี Evidence หรือ Policy ที่ยืนยัน ไม่ควรเดา:** เช่น ระยะเวลาผ่อนผัน หรือสิทธิ์การกดปิดเครื่องเสีย ต้องลงบันทึกเป็น Open Question หรือ Issue เพื่อรอการยืนยัน
- **Requirement ที่ยังมีข้อมูลไม่ครบสามารถเก็บไว้เป็น Needs Follow-up ได้:** เช่น การอัปเดตสถานะผ่าน Sensor หรือ Simulation สามารถเก็บไว้ใน Issue Hold โดยไม่ต้องตัดฟีเจอร์ทิ้ง
- **ทุก Requirement ควร Trace กลับไปยัง Evidence หรือ Need ได้:** เช่น FR-01 ถึง FR-06 สามารถไล่กลับไปหา `E-01` ถึง `E-06` ใน Evidence Log ได้ทั้งหมด
- **Backlog ที่ดีต้องบอกทั้ง “ทำอะไรต่อ” และ “อะไรยังไม่ควรทำ”:** การระบุ `Won't Have` (เช่น ระบบจ่ายเงินออนไลน์/IoT) ช่วยป้องกัน Scope Creep และทำให้ทีมโฟกัสกับเป้าหมายหลักได้ชัดเจน
