## G1.1 บันทึก CR-FX-01

**ผู้เสนอ:** ผู้บริหารหน่วยงานเจ้าของระบบ ในบริบทนี้คือผู้บริหารหอพัก ตามบทบาทในโจทย์ ไม่ใช่หลักฐานการเสนอจริงจากบุคคลที่ระบุชื่อ

**สถานะ:** Pending; Decision ของทีมเป็น Proposed เท่านั้น

**ขอเปลี่ยน:** (1) แจ้งผู้เกี่ยวข้องเมื่อสถานะงานหลักเปลี่ยน โดยผูกกับวงจรคิวซักผ้า (2) เตือนอัตโนมัติก่อนกำหนดสำคัญโดยไม่มีคนกด (3) ให้ผู้ใช้ opt-in รับผ่านช่องทางแจ้งเตือนภายนอก และจำกัดข้อมูลส่วนบุคคลในข้อความ

**เหตุผลที่ผู้เสนออ้าง:** ต้องการทำให้เร็วที่สุดและให้ทุกข้อเป็น Build now ตามโจทย์ ส่วนคุณค่าที่ทีมวิเคราะห์คือช่วยให้นักศึกษาทราบความคืบหน้าคิวและลดการพลาดคิว ไม่ใช่ผลการสัมภาษณ์ใหม่

**Requirement ที่กระทบ:** แก้ FR-04; เชื่อม FR-02, FR-03, FR-05, BR-02; ขยายความเป็นส่วนตัวจาก NFR-01/BR-04 ด้วย NFR-FX-01; เพิ่ม FR-FX-01, FR-FX-02, BR-FX-01 และ DR-FX-01

**Model และ trace:** แก้ US-05/UC-02/AC-05, เพิ่ม US-FX-01 และ AC-FX-01–05; ขยาย trace ให้เดินจาก CR → requirement → model → SRS → ข้อเสนอ Spine/หน้าที่ container → การทดสอบตาม G1.2

**ผลต่อการออกแบบ:** ต้องมีการตรวจเหตุการณ์สถานะ เป้าหมายผู้รับ งานตามเวลา ความยินยอม และการลดข้อมูลก่อนออกภายนอก งานเดิม W10/W11 ยังเป็นแบบฟอร์ม จึง Cannot Verify ชื่อ Spine/container เดิม ข้อเสนอหน้าที่ต่อไปนี้ต้องให้ G3/G4 กำหนดชื่อและตัดสินว่าจะเพิ่ม container หรือไม่

**ผลต่อการทดสอบ:** เพิ่มการทดสอบ event/status, timer ที่ไม่มีผู้ใช้กด, opt-in/opt-out, ผู้รับที่เกี่ยวข้อง และ payload privacy; ใช้ AC-FX-01–05 และตรวจ regression AC-04/AC-05 เดิม

| ทางเลือก | ผลดี | ข้อจำกัด |
|---|---|---|
| A ทำทุกช่องทางและนโยบายใหม่ทันที | ครอบคลุมคำขอเร็วถ้าข้อมูลครบ | ช่องทาง วิธีเชื่อมต่อ เวลา และทรัพยากรยังไม่ชัด เสี่ยงเมื่อเวลาลดครึ่งหนึ่ง |
| B แบ่งส่งมอบ รักษาวงจรคิวและออกแบบจุดเชื่อมต่อภายนอกไว้ | ลดความเสี่ยงจาก TBD และสอดคล้อง CR-FX-02B | การเชื่อมต่อจริงรอคำตอบและการอนุมัติ scope |

**Decision ที่เสนอ:** เลือก B เป็นทิศทางให้ G3 ประเมินระดับ scope แยกรายความสามารถ ไม่รับคำว่า “ทุกอย่าง Build now” โดยอัตโนมัติ คงการตรวจสิทธิ์และการปกปิดข้อมูล ส่วน audit ใหม่เสนอผ่าน FR-FX-04/DR-FX-02/BR-FX-02 ด้านล่าง ไม่อ้างว่ามีใน SRS แล้ว

**ผู้มีอำนาจตัดสิน:** ผู้มีอำนาจอนุมัติ CR ของหน่วยงานเจ้าของระบบ (ตำแหน่ง/ชื่อ TBD) ไม่ถือว่าผู้เสนอหรือทีมออกแบบมีอำนาจอนุมัติโดยอัตโนมัติ

**Next action:** ยืนยันฐาน SRS, หาผู้อนุมัติ, ตอบ OI-FX-01–05 แล้วให้พสิษฐิ์ประเมิน G3/G5 และปฐมพรทำ G4; ทั้งกลุ่มตรวจร่างก่อนรวม Word

## G2.1 User Stories

**US-05 แก้เสนอ — FR-04, FR-FX-01:** ในฐานะนักศึกษาหอพัก ฉันต้องการรับแจ้งเมื่อสถานะคิวของฉันเปลี่ยนและรับเตือนก่อนกำหนดสำคัญโดยอัตโนมัติ เพื่อวางแผนมาใช้เครื่องหรือรับผ้าได้ทัน โดยคงการเตือนก่อนซักเสร็จ 5 นาทีเดิม และรอข้อสรุปนโยบายเวลาใหม่

**US-FX-01 ใหม่เสนอ — FR-FX-02, BR-FX-01, NFR-FX-01, DR-FX-01:** ในฐานะนักศึกษาหอพัก ฉันต้องการเลือกเปิดหรือปิดการรับแจ้งเตือนผ่านช่องทางภายนอกและให้ข้อความมีข้อมูลเท่าที่จำเป็น เพื่อควบคุมการรับข้อความและรักษาความเป็นส่วนตัว

## G2.2 Use Case flow

### UC-02 แก้เสนอ การจองคิวและจัดการวงจรคิว

Primary actor: นักศึกษาหอพัก; supporting external system: ช่องทางแจ้งเตือนภายนอก (TBD วิธีเชื่อมต่อ) ไม่ถือว่าเป็นคนกดงานตามเวลา

Precondition: เข้าสู่ระบบและไม่มีคิวค้างตาม BR-01; การส่งภายนอกต้องมี opt-in และข้อมูลปลายทางที่ใช้ได้ Postcondition: คิวบันทึก/เปลี่ยนสถานะถูกต้อง; ข้อความส่งเฉพาะผู้เกี่ยวข้องตามความยินยอม

| ขั้น | Actor | System |
|---|---|---|
| 1 | นักศึกษาหอพักเลือกเครื่องและกดจอง | ตรวจบัญชี BR-01 และสถานะรับคิว บันทึกคิวและแสดงรหัสคิว |
| 2 | — | เมื่อสถานะคิวเปลี่ยน บันทึก audit ตาม FR-FX-04 พร้อมสถานะ; ระบุเจ้าของคิว สร้างรายการแจ้งเตือนในเว็บตาม FR-FX-03 ตรวจความยินยอมก่อนส่งภายนอก |
| 3 | — | เมื่อเครื่องว่างและถึงคิว แจ้งนักศึกษาและเริ่มเวลาผ่อนผันเดิม 10 นาที โดยไม่ผูกการเดินคิวกับการส่งภายนอกสำเร็จ |
| 4 | นักศึกษาหอพักยืนยันเริ่มใช้งาน | ตรวจเจ้าของคิวและเวลา เปลี่ยนสถานะเป็นกำลังทำงาน เริ่มเวลาซักจำลองตาม CT-01 |
| 5 | ไม่มีผู้ใช้กด | ก่อนเวลาซักจำลองเสร็จ 5 นาที ระบบสร้างรายการแจ้งเตือนในเว็บเอง แม้เจ้าของไม่ได้เปิดเว็บค้าง; นโยบายเตือนใหม่ใช้เมื่อยืนยัน OI-FX-02 แล้วเท่านั้น |
| 6 | นักศึกษาหอพักรับผ้าและยืนยัน | บันทึกผล คืนเครื่องว่าง และประมวลผลคิวถัดไปตามกฎเดิม |

**Alternate 2a:** ไม่ opt-in → ไม่ส่งภายนอก การจองและวงจรคิวทำงานต่อ; การแสดงข้อมูลในระบบคงตาม SRS ระบบต้องสร้างรายการแจ้งเตือนในเว็บให้เจ้าของคิวตาม FR-FX-03 โดยไม่ขึ้นกับ opt-in ภายนอก

**Alternate 4a:** ไม่ยืนยันทัน 10 นาที → หมดสิทธิ์ตาม FR-03 แล้วแจ้งสถานะตาม FR-04 ตรวจ opt-in สำหรับภายนอก

**Exception 2b:** ภายนอกส่งไม่สำเร็จ → ไม่รายงานว่าส่งสำเร็จ ไม่ย้อนสถานะคิวที่บันทึกแล้ว; นโยบาย retry/fallback เป็น TBD ตาม OI-FX-04

### UC-FX-01 ใหม่เสนอ การตั้งค่ารับแจ้งเตือนภายนอก

นักศึกษาหอพักเปิดการตั้งค่าของตนเอง → ระบบแสดง preference → นักศึกษาเลือกเปิด/ปิด → ระบบตรวจเจ้าของบัญชีและบันทึก → แสดงผลการบันทึกสำเร็จ ก่อนส่งครั้งต่อไปตรวจค่าปัจจุบัน; ถ้าไม่มีการยินยอมไม่ส่งภายนอก ข้อมูลปลายทางและการยืนยันช่องทางเป็น TBD

## ส่งต่อ G3/G5 และ G4

เลือก CR-FX-02B: เวลารุ่นแรกเหลือครึ่งหนึ่ง ข้อเสนอให้ตัดสิทธิ์/audit เป็นข้อเสนอของหัวหน้าทีม Dev ยัง Pending

ให้พสิษฐิ์ใช้รายการ G2.4 แบ่ง scope ทั้ง 4 ระดับทีละความสามารถ: event/status, timed reminder, preference/opt-in, external integration และ privacy/data พร้อมเปิด decision สำหรับ OI-FX-01–05 โดยไม่ถือว่า Proposed requirement ทั้งหมดต้อง Build now

ข้อจำกัดที่ต้องรักษาในการลด scope: BR-01 หนึ่งบัญชีหนึ่งคิว, BR-02 ผ่อนผัน 10 นาที, BR-03 ผู้ดูแลเท่านั้นที่ปิดเครื่อง, BR-04/NFR-01 ปกปิดข้อมูลคิวสาธารณะ การตัดการตรวจสิทธิ์ทำให้ผิด BR-03; audit ใน baseline เดิม Cannot Verify; ร่างนี้เพิ่ม FR-FX-04/DR-FX-02/BR-FX-02 แบบ Proposed เพื่อรองรับ G5 โดยไม่อ้างเป็น baseline ที่อนุมัติแล้ว

เส้นทางเชิงหน้าที่เสนอเพื่อทำ Spine: สถานะคิวเปลี่ยน/ถึงกำหนด → ตรวจสถานะล่าสุดและผู้รับ → ตรวจ opt-in หากส่งภายนอก → ลดข้อมูลข้อความ → ส่งผ่านจุดเชื่อมต่อภายนอก TBD. ปฐมพรต้องกำหนดชื่อ container จริง ตำแหน่งรันและผู้ควบคุมใน G4; ไม่มีการฟันธงเพิ่ม container จาก G2 นี้
